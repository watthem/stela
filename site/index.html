the problem

Your chunk offsets are wrong.

Most chunking libraries give you a start_index that says where a chunk came from. That number is a character offset, not a byte offset. It's valid for slicing the in-memory string, but if your pipeline stores it and later uses it to slice the file bytes, accented characters, CJK text, or emoji cause the two to diverge. The gap accumulates through the document.

Store that character offset in a vector database, treat it as a file position later, and you're highlighting the wrong text.

Character vs byte mismatch

LangChain's start_index is a valid character offset, but if you treat it as a byte position, it's off by 24 bytes on a French document with accented characters. No error, no warning.

No verification

Offsets are found after splitting using string search. Token splitters have documented failure cases, and there is no per-chunk hash to catch mismatches at query time.

No stale detection

When a source document changes after indexing, nothing in the chunk metadata tells you which chunks are now invalid. You serve stale answers without knowing.

what stela does

01
Tracks offsets during the split
Byte positions are recorded as the splitter walks the document. No search step afterward. The position is known at split time.
02
Verifies every chunk
Before emitting a chunk, the pipeline slices the original file at the byte range, recomputes the SHA-256 hash, and checks they match. If they don't, it throws.
03
Detects stale documents
Store the content hash alongside your vectors. When a source file changes, recompute and compare. Every invalid chunk is identified.
